# App Routing (`helprest-app/app`)

## Purpose and Design Decisions

Implements file-based navigation with Expo Router v5 across four route groups:

- `_layout.tsx` — Root `QueryClientProvider` and session/onboarding gatekeeper (with `(app)/_layout.tsx` re-checking `loadTokens()`, `loadUserProfile()`, and incomplete consumer onboarding on segment transitions).
- `(auth)/` — Google OAuth-only login (`home.tsx`, with `isCompanyMode` toggle; legacy local email/password login was removed), 6-step consumer registration (`register/step1..step6.tsx`), and 3-step establishment registration (`register-establishment/step1..step3.tsx`).
- `(app)/(tabs)/` — Consumer bottom tabs: `(home)` discovery/recommendations, `(places)` search & map/list, `(favorites)` saved establishments/products, and `(social)` community visit feed.
- `(app)/(establishment)/` — Establishment admin portal (`dashboard.tsx`, `menu.tsx`, `product-form.tsx`), plus modal/detail routes `details/[id].tsx`, `product/[id].tsx`, and `visit/create.tsx`.

## Invariants

- **OAuth-Only Login (`app/(auth)/home.tsx`)**: Authentication is exclusively Google OAuth2 (`signInWithGoogle()`), routing new users either to `(auth)/register/step1` or `(auth)/register-establishment/step1` based on `isCompanyMode` and `saveCompanyOnboardingStatus()`.
- **Root Session & Role Routing (`app/_layout.tsx` & `app/(app)/_layout.tsx`)**:
  - On mount, `validateSession()` checks `loadTokens()`. Without tokens, it routes to `/(auth)/home`.
  - With tokens, it validates against `GET /api/users/me`, caches the profile via `saveUserProfile()`, and checks `getIncompleteOnboardingStep(profile)`. If incomplete (for non-establishment users), it redirects to `/(auth)/register/step<N>`.
  - When authenticated and complete, establishment accounts route to `/(app)/(establishment)/dashboard`, whereas consumers route to `/(app)/(tabs)/(home)`.
  - On network errors during startup, `_layout.tsx` attempts `POST /api/auth/refresh` before falling back to `loadUserProfile()` offline cache.
- **Role Contract Alignment Warning (`api-http` vs `app-routing`)**: Mobile code currently checks `profile.role === "establishment"` and sends `{ role: "establishment" }` to `PATCH /api/users/me` (`home.tsx`, `register-establishment/step3.tsx`), whereas `helprest-api` validates `"establishment_admin"` on `PATCH /api/users/me` (`user.module.ts`), requires `"establishment_admin"` on `POST /api/establishments`, and serializes `Role` object `{ value }` in `GetUserProfile`. Any change to establishment onboarding must reconcile this client/server role contract.
- **Client-Side Visit Photo Geofencing (`app/(app)/visit/create.tsx`)**: Before allowing a user to attach/submit visit photos, the screen checks device GPS coordinates against the establishment's coordinates (`100m` radius) to match the backend invariant in `api-application` (`CreateVisit`).

## Integration Contracts

- Consumes `api`, `signInWithGoogle`, and `getCurrentPosition` from `app-services`, token/profile helpers from `app-storage`, query hooks and `queryKeys` from `app-queries`, and UI primitives from `app-components`.

## Anti-Patterns

- Bypassing `_layout.tsx` session state by navigating directly to `/(app)/(tabs)` without persisting tokens via `saveTokens()` and profile state via `saveUserProfile()`.
- Routing establishment admin accounts (`establishment` / `establishment_admin`) into consumer onboarding steps or consumer tabs without checking `profile.role`.
